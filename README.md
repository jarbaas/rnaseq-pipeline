# Overview

Production-grade Nextflow DSL2 pipeline processing bulk RNA-seq data from raw FASTQs generated by Illumina FASTQs into a count matrix for downstream DEG analysis. Pipeline is designed to handle longitudinal data from drug treatment studies containing biological replicates. 

## Architecture
Modular design utilizing existing nf-core/rnaseq modules. Custom build allows for replacing/rearranging models depending on project needs. 
- **FASTQC:** Performs initial quality checks on FASTQ
- **FASTP:** Adapter trimming and low-quality base removal
- **FASTQC:** Compiles quality report on trimmed reads
- **PARABRICKS_RNAFQ2BAM**: GPU-accelerated STAR alignment and BAM generation, prioritizing speed and accuracy
- **featureCounts:** Counts sequencing reads mapping to genomic reference
- **Aggregation:** Python/Pandas module builds featureCount outputs into single count matrix
- **MultiQC:** Aggregates logs into final HTML report

## Scenario Questions
*How would you design the input schema and Nextflow channels to dynamically handle the varying replicates across different time points*

The input for this pipeline is a samplesheet CSV file containing sample_id, timepoint, treatment, replicate, fastq_1 and fast_2 headers. The nf-schema module validates the samplesheet at launch to ensure these columns are in the CSV and the filepaths stored in the fastq columns are properly formatted. The CSV is then parsed via a queue channel that emits a separate tuple for each row of the file. The Nextflow pipeline will dynamically execute each tuple asynchronously across the modules before collecting them together to build the matrix, so the replicant count for a given sample can vary without affecting the pipeline execution. 

*How would you structure the pipeline to ensure it is easily scalable, modular, and cloud-ready? The cloud has access to both CPU and GPU and speed and accuracy are important factors.*

The pipeline is modular and scalable because it uses individual modules from nf-core/rnaseq, meaning these modules can be rearranged or replaced easily without having to alter the entire pipeline. It is also scalable by allowing for any number of replicates, timepoints, etc. so a new, larger experiment could still use the same pipeline. The GPU-enabled STAR alignment step vastly reduces runtime while providing BAM file outputs for an informative and accurate QC review. The pipeline uses Docker containers integrated into modules to ensure portability and reproducibility. It also features standard and portable profiles, allowing the pipeline to be run locally or in any cloud platform.  

*How would you explain the required input format (e.g., the sample sheet) to me, and how will your pipeline validate that I haven't made a mistake?*

The input file is a sample sheet CSV with six columns: sample_id, treatment (vehicle or drug label), timepoint, replicate, fastq_1, fastq_2. Simply fill in the metadata columns with the appropriate information, and write the filepaths to the paired reads generate from Illumina in the fastq columns. The pipeline will automatically validate you have set the file up correctly, and will not run if a particular column name or input format needs adjustment.

*Suppose I come to you in a panic because Day 5 only yielded 2 viable replicates instead of 5, and one of the Day 13 samples failed QC mid-run and I have no DE genes.*

*Explain to me how your pipeline handles these failures without crashing the entire run, and what I will see in the final output.*

Firstly, the number of replicates for any particular sample or day will not matter to the pipeline, because it process each independently and asynchronously. There is no need to worry about the replicant count breaking the pipeline. However, you should be aware that the statistical power of that sample will be reduced due to the lower number of replicates. 

If one of the Day 13 samples fails mid-run, you will notice one of two things. The column for that sample in the count matrix will have mostly zeros for gene counts. In that scenario, we can look at the FastQC report and see which sample likely failed, and remove it from the matrix. The pipeline automatically generates a report in the results folder upon completion. If a poor sample triggers an error, the pipeline will ignore it and continue processing the rest, and it will not be featured in the final count matrix. We can then look at the report and see which sample triggered the failure. The importance of producing the BAM files with the STAR alignment is it allows us to run further QC diagnostics in case one of our samples has a problem. 

## Run Command
An example of a run command on a cloud platform:

```
nextflow run main.nf \
    -profile portable \
    --input sample_sheet.csv \
    --fasta example.fa \
    --star_index ./directory \
    --gtf example.gtf
    --outdir ./results
```
*Note that -stub can be included in the run command for workflow validation. -resume can be included to used cached information in case the pipeline is to be rerun for any reason.*

## Deliverables 
Upon completion, the pipeline automatically defaults the following files to the results/ directory:

- `counts/gene_counts.tsv`: The count matrix prepared for downstream differential expression analysis.
- 
- `counts/count_manifest.tsv`: TSV record of which samples were processed by featureCounts and integrated into the count matrix.

- `MultiQC/multiqc_report.html`: An HTML report detailing read survival rates, alignment scores, and specifics on why any dropped samples failed mid-run.

- `pipeline_info/pipeline_dag.html`: A Directed Acyclic Graph mapping the data flow of the completed run.

- `pipeline_info/pipeline_report.html`: An HTML report detailing runtime metrics and execution data, flagging any samples that may have failed QC and were ignored by the pipeline.
